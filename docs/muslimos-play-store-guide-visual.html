Executive Summary

Ship MuslimOS to Android without losing the product’s elegance.

The right move here is disciplined, not dramatic: protect the current app, harden it for mobile, and only introduce heavier architecture when the product earns it.

Best Fit

Capacitor + current app

Fastest route to release, lowest rewrite risk, and the cleanest way to preserve the UI quality already built into MuslimOS.

SQLite

Optional, not mandatory

Useful later for heavy offline content and structured storage. Not a reason to block a first Android release.

MuslimOS Recommendation Treat Android launch as a product packaging project first, not a rewrite project. Ship the current experience in a native shell, then deepen native infrastructure later.
Architecture

Choose the least destructive path.

The elegant solution is the one that protects visual quality and shipping velocity at the same time.

Path Why it fits Use when
Capacitor + current app Keeps the existing Vite + React codebase alive and avoids rebuilding the UI from scratch. You want a serious Android release soon with minimal technical waste.
Flutter rewrite Strong native control, but it resets product velocity and forces a full UI rebuild. You are planning a larger platform rewrite anyway.
React Native rewrite Shared JavaScript skills, but still a major migration with a lot of integration churn. You need deeper native UI later and accept a rewrite cost now.
Storage Strategy

Only add a database when the product truly needs one.

Don’t burden v1 with infrastructure that sounds mature but slows delivery without improving the user experience.

Keep simple storage for now

Good for v1

  • settings and language
  • streaks and bookmarks
  • last-read position
  • checklists and tasbeeh state
  • light journal entries
Add SQLite later

Use when scale becomes real

  • offline hadith bundles
  • downloaded tafseer packs
  • large search indexes
  • sync-ready local data models
  • heavier long-term journaling data
Phase 1: no SQLite block Phase 2: migrate if needed Phase 3: optimize for scale
Implementation

Move from web app to Android product in practical phases.

The sequence below is built for MuslimOS specifically: protect what already works, then add native polish deliberately.

Phase 1
Stabilize the existing app for mobile shell use

Audit mobile viewport quality, audio behavior, Android back handling, safe areas, and persistence across all major flows.

Phase 2
Add Capacitor and Android Studio release flow

Package the built app, configure Android, and establish a proper release pipeline around signed bundles.

Phase 3
Add native polish where users feel it

Splash, icons, status bar, notifications, and permission flows should feel deliberate and trustworthy.

Phase 4
Ship internal, then public

Use internal and closed testing first, then move to production once crash-free behavior and QA confidence are strong enough.

npm install @capacitor/core @capacitor/cli npx cap init npx cap add android npm run build npx cap sync android npx cap open android
Native Scope

Add native polish where Android users will actually feel it.

This is the layer that makes MuslimOS feel like an app, not a website inside a frame.

High priority

What should be native early

  • splash screen
  • icons and launch branding
  • status bar styling
  • Android back behavior
  • local notifications
Optional later

Only when product scope grows

  • SQLite-backed offline content
  • background jobs
  • sync/account architecture
  • biometric privacy for journal
QA

Do not submit a worship app with unstable basics.

MuslimOS should feel calm, clear, and dependable on real Android devices.

□Home, Quran, Worship, Hadith, and drawer navigation all behave correctly on device
□Surah and ayah audio remain stable across background, resume, pause, and seek
□Tafseer language follows the global app language every time
□Islamic Calendar and Hijri date resolve correctly for the user’s local region
□Journal and Worship tracker persist local state without loss
□Qibla permission failures show a graceful and understandable fallback
□No horizontal scroll, broken safe areas, or awkward bottom-nav collisions on Android

Keep the current MuslimOS app. Package it with Capacitor. Ship Android first. Add SQLite only when offline structured data genuinely becomes a product requirement. That path is technically sound, fast to market, and aligned with the quality already present in the product.
